# SW002 Reference Architecture

[docs](../index.md) / [reference](./) / SW002 Reference Architecture

> **Status: Historical reference** -- This document describes the SW002 implementation that used Istio Ambient Mode for DFSP mTLS. Mojian uses Cilium + standalone Envoy instead. See [DFSP mTLS](../architecture/dfsp-mtls.md) for the current architecture and [ADR-002](../architecture/decisions/002-cilium-over-istio.md) for the decision rationale.

## Overview

SW002 was a reference implementation from InFiTx that used Istio Ambient Mode for transparent mTLS between the Hub and DFSPs. It served as the design input for Mojian's partner edge architecture.

The implementation demonstrated that per-DFSP certificate management and dynamic routing configuration could be driven entirely from Vault, with MCM as the enrollment interface. Mojian adopted this flow while replacing the underlying service mesh.

## Architecture (Istio Ambient)

SW002 used Istio's Ambient Mode, which splits L4 and L7 concerns into separate components:

- **ztunnel DaemonSet** -- L4 mTLS termination and origination, transparently intercepting pod traffic
- **Waypoint proxies** -- L7 policy enforcement, deployed per-namespace or per-service
- **ServiceEntry + DestinationRule per DFSP** -- Outbound routing to external DFSP endpoints with TLS origination
- **Egress waypoint** -- Per-DFSP `UpstreamTlsContext` loaded from Kubernetes Secrets (sourced from Vault)
- **Vault Agent sidecar** -- Watched Vault KV paths, rendered Kubernetes resources via Go templates

The inbound path terminated mTLS at an Istio ingress gateway, validated client certificates against a per-DFSP CA bundle, and routed to the internal FSPIOP API.

## What Mojian learned from SW002

The following patterns were adopted directly or adapted:

- **Vault Agent template pattern** -- Dynamic generation of per-DFSP Kubernetes resources from Vault KV data. Mojian uses the same Vault Agent ConfigMap approach with adapted templates for CiliumEnvoyConfig and Envoy resources.
- **Per-DFSP resource model** -- Each DFSP gets its own Secret (certs), routing configuration, and network policy. Mojian maps this to: Secret + CEC snippet (outbound) + Envoy SDS entry (inbound).
- **MCM enrollment flow** -- MCM creates DFSP in Vault PKI, stores certs in Vault KV, Vault Agent picks up changes and regenerates resources. This flow is identical in Mojian.
- **Certificate lifecycle** -- Vault PKI intermediate CA issues DFSP-specific client/server certificates with configurable TTL. Renewal is handled by MCM triggering a new cert issuance in Vault.

## Why Mojian chose differently

See [ADR-002](../architecture/decisions/002-cilium-over-istio.md) for the full decision record.

In summary:

- **No additional DaemonSet** -- Cilium was already the CNI on all providers. Adding mTLS via CiliumEnvoyConfig (CEC) reuses Cilium's existing Envoy DaemonSet, whereas Istio Ambient requires ztunnel (a separate DaemonSet) plus waypoint proxies.
- **Explicit over transparent** -- Istio Ambient transparently intercepts traffic via iptables/eBPF redirection. Mojian uses explicit `CiliumNetworkPolicy` listener redirect for inbound and CEC route configuration for outbound. This is more debuggable: `cilium monitor` and Envoy access logs show the exact path.
- **Simpler architecture** -- CEC for outbound mTLS origination + standalone Envoy Deployment for inbound mTLS termination covers all DFSP mTLS cases. No waypoint proxies, no ServiceEntry/DestinationRule CRDs, no Istio control plane.
- **Operational consistency** -- A single CNI (Cilium) handling networking, network policy, Gateway API, and DFSP mTLS reduces the number of moving parts and the knowledge required to operate the platform.
